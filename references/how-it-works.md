# 这套规范怎么运作

理解机制才能正确使用。四个设计选择决定了它的全部行为。

## 一、分层加载：为什么入口必须短

`AGENTS.md` 限制 150 行，不是审美要求。

原因：模型读长文档时，**开头的内容权重远高于结尾**。一份 400 行的"万能规范"会让模型只记住前 50 行，后面 350 行等于没写——但它又占据了每次会话的上下文。

所以结构是：

```
~/.ai-dev-standards/            全局，所有项目共用
├── AGENTS.md（≤150 行，每次会话都读）
│   ├── 优先级与规则强度
│   ├── 工作方式（诊断先行、一次一件事、不伪造结果）
│   ├── 自动探测表（看到什么文件 → 加载什么模块）
│   ├── 分流表（在做什么事 → 必读什么模块）
│   ├── 10 条跨语言红线
│   └── 完成定义（DoD）
└── .agents/（按任务加载，一次通常只读 1-2 个）
    ├── commit.md             写提交信息时读
    ├── discipline.md         提交、碰凭据、收尾时读
    ├── integration.md        对接外部系统时读
    ├── legacy.md             改老项目时读
    ├── task-workflow.md      跨会话、拆子任务时读
    ├── lang-java.md          改 Java 时读
    ├── lang-android.md       改 Kotlin / Compose / Room 时读
    ├── lang-python.md        改 Python 时读
    ├── lang-vue.md           改前端时读
    ├── release-github.md     发版时读
    ├── release-android.md    打 APK、配签名时读
    ├── release-docker.md     改镜像时读
    └── release-gitee.md      Release 附件同步到 Gitee 时读

<项目>/
├── AGENTS.md                 指针：告诉我规范在哪、按什么顺序读
├── CLAUDE.md                 一行 @AGENTS.md
└── .agents/project-profile.md  项目事实，唯一按项目改的文件
```

**为什么模块不放在项目里**：14 个模块和具体项目无关，复制 N 份的直接后果是升级要跑 N 次、改一条规则要同步 N 个仓库。放进全局目录后，升级只跑一次。

代价是规范跟着机器走，不跟着仓库走——同事 clone 只拿到指针，需要自己装一次全局。这一点在 README 的「团队协作」里写清了取舍。

**分流表是这套体系的开关。** 新增模块必须同时登记触发条件，否则永远加载不到——`scripts/check.sh` 的第 3 项检查就是拦这个。

## 二、规则分三档：为什么必须分

不分档的规范等于没有规范：全是"最好这样"，执行时就全靠模型心情。

| 档位 | 含义 | 违反后果 |
| --- | --- | --- |
| `【红线】` | 永不，无例外 | 返工 |
| `【默认】` | 按此执行，除非 profile 或用户明确覆盖 | 需要说明理由 |
| `【建议】` | 自行权衡 | 偏离时说明理由即可 |

判断一条规则该放哪档，问一句：**违反它会造成不可逆损失吗？**

- 真实邮箱推上公开仓库 → 不可逆 → 红线
- 提交信息格式 → 可修正 → 默认
- 函数命名风格 → 无所谓 → 建议

红线要少而硬。一个文件里出现 20 条"红线"，等于没有红线。

## 三、门禁：为什么规范需要会失败的检查

写在文档里的规则，遵守率取决于人的自觉。加一道会失败的检查，遵守率变成 100%。

新结构下门禁分两层，各管一段：

```
1. commit-msg 钩子（提交时，在项目里）
   格式不对直接拒绝提交。类型大小写、单号、AI 署名。
   → 拦在本地，成本最低。由项目初始化时装进 .git/hooks/

2. scripts/check.sh（改规范仓库时）
   入口行数、明文邮箱、模块登记、交叉引用、代码块闭合、数字对账、插件清单。
   → 拦在规范本身出问题之前
```

**项目级的规范自检门禁没有了。** 老版本会把 `check.sh` 和 `.github/workflows/check.yml` 复制进项目，CI 里跑一遍。新结构下项目里没有模块，那些检查项（模块登记、分流表断链）也不成立了。

如果你确实想在项目 CI 里卡一道，可行的做法是在 workflow 里先 clone 规范仓库再跑它的 `check.sh`——但那检查的是规范，不是你的项目，收益有限。**项目真正需要的门禁是构建、测试、安全扫描**，那属于项目自己的 CI，不归这套规范管。

设计要点：**门禁失败必须给出可操作的修复指引**，不能只说"格式错误"。看 `commit-msg` 的输出就知道该怎么改。

## 四、优先级：冲突时听谁的

```
1. 用户在本次会话的明确指令
2. .agents/project-profile.md 的项目声明
3. 全局 AGENTS.md + .agents/ 模块
4. 模型的默认习惯
```

第 2 条高于第 3 条是关键设计：**项目事实高于通用建议**。一个 Java 8 的老项目，`lang-java.md` 里关于虚拟线程的建议就该被 profile 的 `java: 8` 压住。

## 五、为什么模块不会自动加载

`AGENTS.md` 只是文件，不是插件。没有任何机制保证模型读了它。

新结构下起作用的是三件事：

1. 项目 `AGENTS.md` 指针（模型读到后知道"真正的规范在全局目录"）
2. 全局 `AGENTS.md` 里的分流表（知道"该加载什么"）
3. **用户开场的显式指令**（没装插件时）

所以没装插件的项目，开工第一句要说：

> 先读全局的 AGENTS.md 和 .agents/project-profile.md，再按分流表加载本项目需要的模块。

这句话的作用是把"读文件"这个动作显式化。不说，模型可能直接开始改代码。

装了 Claude Code 插件时，`hooks/session-context.sh` 会在会话启动时把状态和路径直接送进上下文，替代这句开场白。它只读、不写任何文件。

**指针方案依赖一个前提**：工具允许模型读工作区外的文件。Claude Code 首次读全局目录可能弹一次权限确认；个别限制工作区外读取的工具，只拿得到指针里那几行。这种情况把需要的模块复制进项目 `.agents/`，并在项目 `AGENTS.md` 里改成读本地副本。

## 六、这套体系约束不了什么

- **工具链没覆盖的地方**：真正的门禁还是 CI 的构建、测试、安全扫描。这套规范只管"怎么写"，不管"能不能跑"。
- **模型能力边界**：规范能让模型少犯错，不能让模型会它不会的东西。
- **人的判断**：规则是下限，不是上限。写不出触发条件的规则应该删掉，而不是留着凑数。
