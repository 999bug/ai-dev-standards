# reviews/：待审批的经验提取报告

从具体项目里挖到的经验，**先出报告，审批通过才合并进 `.agents/`**。这样 `.agents/` 里的每条规则都能追到一次真实事故，而不是收集来的口号。

## 目录约定

| 文件命名 | 内容 |
| --- | --- |
| `YYYY-MM-DD-<项目>-<技术栈>.md` | 该项目的提取报告，按「日期-项目-技术栈」命名，例如 `2026-11-15-demo-java` |

一份报告至少回答四件事：

1. **素材来源**：哪个项目、什么技术栈、涉及哪些模块/目录。
2. **候选规则**：逐条写「现象 → 根因 → 建议规则 → 规则强度（红线/默认/建议）」。
3. **落到哪**：拟合并进哪个模块的哪一节；已有规则能覆盖的，直接标注「已覆盖，不新增」。
4. **审批结论**：通过 / 部分通过 / 驳回，以及驳回理由——**驳回的也要留证据**，否则下轮会被重复讨论。

## 合并原则

- 一条候选规则合并前先问：**删掉这条规则，会导致同类的坑再踩一次吗？** 答不上来就不加。
- 只写这门语言/这套系统**特有的坑**，通用纪律不抄（见 `AGENTS.md` 第 8 节）。
- 报告合并后**不删除**，作为规则的出处保留；`.agents/` 里对应条目应在文末注明来源报告。
